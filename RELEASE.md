# Releasing Piyo AI

How a version is numbered, built, checked, published and, if it goes wrong, taken back. Written for whoever cuts the
next release; every command here is run from the repository root (`PiyoAI/`) unless it says otherwise.

In one paragraph: you bump the version, commit, push, wait for CI, then push a tag `vX.Y.Z`. That tag makes GitHub
Actions build the installers on Windows, macOS and Linux and attach them, with the update manifest, to a **draft**
release whose text is written from the commit subjects. Nothing is public until you review the draft and press
**Publish**. Publishing is also what makes running copies of Piyo offer the update.

## Versioning

- **Scheme.** `MAJOR.MINOR.PATCH`, written `0.3.0` in files and `v0.3.0` in tags. While Piyo is `0.x` we have used:
  a new **minor** for a release with new features (`0.2.0` → `0.3.0`) and a new **patch** for fixes only
  (`0.1.1`, `0.1.3`, `0.1.5`). The version is plain digits: no `-beta` suffix (the bump script and the updater
  compare numbers, and `release_notes.py` orders tags by their digits).
- **One version for everything.** The desktop app, the Rust shell and the Python core ship together and share a number.
  It is written in these places, and `scripts/bump_version.py` changes all of them:

  | File | What it holds |
  |---|---|
  | `apps/desktop/src-tauri/tauri.conf.json` | the version the installers and the updater use |
  | `apps/desktop/src-tauri/Cargo.toml` and `Cargo.lock` | the shell crate `piyo-desktop` |
  | `apps/desktop/package.json` and `package-lock.json` | the UI (the lock repeats it twice) |
  | `core/pyproject.toml` and `uv.lock` | the core package `piyo` |
  | `core/piyo/__init__.py` | `__version__`, what `/api/health` reports |

- **A check, not trust.** `python scripts/check_version.py` fails if those files disagree, and
  `python scripts/check_version.py v0.3.0` also fails if the tag does not match them. `bump_version.py` runs the first when it
  finishes; the release workflow runs the second before it builds anything, so a mistyped tag cannot ship the wrong
  number. (Regular CI does not run either, so a hand edit of one file is only caught at release time.)
- **The catalog is versioned separately.** The skill catalog lives in `Piyo-AI/piyo-skills` and has its own history
  and signed `index.json`; releasing the app does not release the catalog (see *Other things that ship* below).

## Commit subjects are the changelog

The release text is generated by `scripts/release_notes.py` from the commits since the previous tag, so write subjects
for a reader, in the imperative.

- Prefix a subject with `feat:` (listed under **New**), `fix:` (**Fixed**) or `security:` (**Security**). No prefix
  lands under **Changes**.
- `chore:`, `ci:`, `docs:`, `test:` and `build:` commits, merge commits and `Version x.y.z` commits are left out.
- A body line starting with `- ` is listed under its commit; a bullet wrapped onto indented lines is joined.
- Preview the text for a tag before you push it:

  ```bash
  git fetch --tags
  python scripts/release_notes.py HEAD --previous v0.3.0     # before tagging; the heading says HEAD instead of the tag
  python scripts/release_notes.py v0.4.0                     # after tagging: exactly what the release will say
  ```

  The ref must exist in your clone, which is why the first form uses `HEAD`. The footer (unsigned build, Chromium downloads on first
  use) is `FOOTER` in that script; change it there, for example once the builds are signed.

## Before you cut a release

1. **`main` is green.** The CI run for the commit you are releasing passed on all three systems (core tests, UI,
   Tauri shell, packaged core, licence check).
2. **Everything CI runs passes on your machine:** `python scripts/check.py` (ruff, pytest, typecheck, UI build).
3. **Licence notices are current.** If `uv.lock`, `Cargo.lock`, `package-lock.json`, `core/piyo/skills/helper_tools.json`
   or the app icon changed since the last release, regenerate and commit `THIRD-PARTY-NOTICES.txt`:

   ```bash
   cd core && uv run python ../scripts/licenses.py      # rewrites the file; add --check to only verify
   ```

   CI fails on a licence outside the allowed list, and the installers bundle this file with `LICENSE`.
4. **Bundled tools are the ones you meant.** `uv` and Deno are not in the installer; the core downloads the versions
   pinned (with SHA-256) in `core/piyo/skills/helper_tools.json`. Upgrade steps are in CONTRIBUTING.md.
5. **Docs say what the code does.** `README.md`, `docs/user-guide/`, `PRIVACY.md` (it must match what telemetry and
   the network code actually do), `PLAN.md`'s Decision Log for any changed decision, and `CLAUDE.md` for commands.
   In the workspace's `docs/` repo, tick finished tasks and update the phase status.
6. **Nothing secret in the diff.** Keys, tokens and `.env` stay out of git (`git diff v<previous>..HEAD` is worth a
   skim). The public telemetry keys in `core/piyo/telemetry.py` are write-only client keys and are meant to be there.

## Cutting a release

Replace `0.4.0` with the new version.

```bash
# 1. Set the version everywhere and check the files agree
python scripts/bump_version.py 0.4.0

# 2. Commit it (this exact subject style is skipped from the notes)
git add -A && git commit -m "Version 0.4.0"

# 3. Push the branch and wait for CI to go green on that commit
git push origin main
gh run list --branch main --workflow CI --limit 1

# 4. Tag that commit and push the tag: this starts the release build
git tag -a v0.4.0 -m "Piyo AI 0.4.0"
git push origin v0.4.0
```

Pushing the tag (not the branch) is what starts `.github/workflows/release.yml`. Do it only after CI on the version
commit is green: the release build takes about 10 to 15 minutes and fails late if something is wrong.

### What the release workflow does

1. **Release notes** (Ubuntu): runs `release_notes.py` over the full history and tags.
2. **Installer**, once per system, in parallel:

   | System | Runner | Installers |
   |---|---|---|
   | Windows x64 | `windows-latest` | NSIS `.exe` |
   | macOS, Apple Silicon | `macos-latest` | `.dmg` (built for macOS 13.5 and newer) |
   | Linux x64 | `ubuntu-22.04` | `.AppImage`, `.deb`, `.rpm` |

   Each one: checks the tag equals the version in the files, builds the packaged core with PyInstaller and
   smoke-tests it (`scripts/build_core.py --smoke`), checks the core's native files do not need a newer OS than we
   support (`scripts/check_targets.py`), builds the installer with `tauri-action`, signs the update package, and checks
   the desktop program the same way. The installers are also kept as workflow artifacts.
3. The first finished job creates the **draft** release `Piyo AI vX.Y.Z` with the generated notes; the others add their
   files to it. Together they upload `latest.json`, the update manifest.

To get installers without a release (for example to try a build), run **Actions > Release > Run workflow** by hand: it
builds everything, makes no release and keeps the files as workflow artifacts.

### Review the draft, then publish

Open the draft (`gh release view vX.Y.Z --web`, or the Releases page) and check:

- the notes read well (edit the text in the release if a subject is unclear: the commit history is not changed);
- every installer is attached, plus `latest.json`. For 0.3.0 the draft held `Piyo.AI_<v>_x64-setup.exe`,
  `Piyo.AI_<v>_aarch64.dmg`, `Piyo.AI_<v>_amd64.AppImage`, `.deb` and `.rpm` (the rpm is named `Piyo.AI-<v>-1.x86_64.rpm`),
  with a `.sig` next to the Windows and Linux ones;
- open `latest.json` and look at its `platforms`: each system that should auto-update needs an entry
  (`windows-x86_64`, `linux-x86_64`, `darwin-aarch64`). A missing platform means those users are silently never offered
  the update. History: 0.3.0 and earlier had no macOS entry, because the macOS job built only the `.dmg` and the updater
  needs the `.app.tar.gz` update bundle and its `.sig`; since 0.3.1 the macOS job builds `app,dmg` (`release.yml`) and a Mac
  on 0.3.0 or earlier is offered 0.3.1 by the normal update flow. If you change `bundles`, re-check this list;
- ideally, install one build on a clean machine and start it, and, for any release after the first, update to it
  from the previous version (Settings > Updates, or the update toast).

Then press **Publish release**. It must be published as a normal release, not a pre-release and not left as a draft:
the app looks for updates at `https://github.com/Piyo-AI/PiyoAI/releases/latest/download/latest.json`, which GitHub
serves only for the newest published, non-pre-release release. Publishing therefore also announces the version to
every running copy of Piyo (they see an update toast and decide when to download it).

After publishing: update the `docs` repo (status of the phase, what shipped) and tell people where the downloads are
(<https://github.com/Piyo-AI/PiyoAI/releases>).

## Updates and rollback

- **Signing the update packages.** `tauri.conf.json` holds the updater's **public** key. The matching private key and its
  password are repository secrets, `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, used by the
  release build to sign each update package. The app refuses a download whose signature does not match.
  **Keep a backup of that private key somewhere safe and offline.** If it is lost, existing installations cannot
  verify any new update and users would have to download a fresh installer by hand. Never change the public key
  in `tauri.conf.json` without a plan for the same reason.
- **What users see.** Piyo checks for a new version when it starts and shows a toast (bottom right): **Download** runs in
  the background with progress, then **Install and restart** warns that Piyo will close and start again before it does.
  Settings > Updates shows the same state. Nothing downloads or installs without the user asking.
- **Rollback.** Before installing, the app records the version it is leaving. If the new version starts twice without
  ever reaching a healthy state, the next start offers (native dialog, works without the web UI) to reinstall the
  previous version from that release's own `latest.json`, and the Updates page then warns before offering the bad
  version again (`bad-versions.json`). So a previous release must stay published for rollback to have somewhere to go.
  Implementation: `apps/desktop/src-tauri/src/rollback.rs`.

## Platform floors

The oldest systems we promise to run on are set in one place: `MAX_GLIBC` (2.35, Ubuntu 22.04) and `MAX_MACOS` (13.5)
in `scripts/check_targets.py`, together with the `MACOSX_DEPLOYMENT_TARGET` in the workflows, `minimumSystemVersion` in
`tauri.conf.json`, the runner for Linux (`ubuntu-22.04`) and `docs/user-guide/install.md`. Change them together. There is
no Intel Mac build.

## Unsigned builds

Installers are not code-signed yet (Windows Authenticode, Apple signing and notarisation). Windows SmartScreen and macOS
Gatekeeper warn on first launch; the user guide tells people how to get past them, and the generated release notes say
so. (The update packages **are** signed, with the key above; that is separate from code signing.) When signing is set up,
add the certificates as repository secrets, pass them to `tauri-action` in `release.yml`, and remove the "unsigned"
wording from `FOOTER` in `scripts/release_notes.py`, `docs/user-guide/install.md` and the workflow comment.

## If something goes wrong

- **Wrong version or a broken build, draft not yet published.** Delete the draft release and the tag, fix it, then tag
  again:

  ```bash
  gh release delete vX.Y.Z --yes
  git push origin --delete vX.Y.Z && git tag -d vX.Y.Z
  ```

- **Already published.** Do **not** move or reuse a published tag: people (and the updater) have already seen it. Fix the
  problem on `main` and release the next patch version. To stop new users getting a bad release in the meantime, edit
  it on GitHub and mark it **pre-release** or revert it to draft: the "latest" pointer then falls back to the previous
  published release, which is what `latest.json` resolves to.
- **The tag does not match the files.** The workflow's first step fails with both numbers. Delete the tag (above), run
  `bump_version.py` again, commit, and re-tag.
- **A job fails on one system.** Read that job's log; builds are not retried automatically. `fail-fast` is off, so the other
  systems still finish. Re-run the failed job from the Actions page, or delete the draft and tag, fix, and start over.

## Other things that ship

- **The skill catalog** (`Piyo-AI/piyo-skills`): its `index.json` is signed with an Ed25519 key by
  `piyo-skills/scripts/sign_index.py`, and the app only trusts public keys listed in `TRUSTED_KEYS`
  (`core/piyo/skills/signing.py`). The private key is kept outside every repository and must never be committed. A
  catalog change is just a commit there; it needs no app release unless the trusted keys or the index format change.
- **The workspace plan** (`docs` repo): not part of a release, but update its status tables when one ships.
